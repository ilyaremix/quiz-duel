# Quiz Duel - подробно по модулям

Короткий обзор, 9 пунктов ТЗ, крайние случаи и запуск - в [README](../README.md). Здесь - как устроена каждая часть и почему так.

## Вопросы

`data/questions.json` - 100 вопросов: 5 категорий (Наука и природа, История и география,
Кино, музыка и книги, Спорт, Технологии и интернет) по 20, в каждой 6 лёгких, 8 средних и 6 сложных.
У каждого вопроса текст и 4 варианта на русском и английском и один общий индекс верного ответа,
поэтому русскоязычный и англоязычный игрок играют одну партию.

```json
{ "id": "sci-01", "category": "science", "difficulty": "easy", "correct": 0,
  "ru": { "text": "Какая планета ближе всех к Солнцу?", "options": ["Меркурий", "Венера", "Марс", "Земля"] },
  "en": { "text": "Which planet is closest to the Sun?", "options": ["Mercury", "Venus", "Mars", "Earth"] } }
```

- **Валидатор** (`packages/shared/src/questions.ts`, zod): ровно 100 / 20 / 6-8-6, уникальные id и тексты,
  4 разных варианта, длина под экран (вопрос до 120 символов, вариант до 40), русская версия на русском,
  в английской нет кириллицы, без пробелов по краям и длинных тире. Возвращает все ошибки сразу.
- **Сервер проверяет базу при старте** и не поднимется с битым файлом. Затем синхронизирует таблицу
  `questions`: добавляет новые, обновляет изменённые, а убранные из файла выключает (`active = false`),
  не удаляя: на них ссылаются сыгранные партии. Повторный запуск без изменений ничего не пишет.
- **Вопросы не попадают в мини-апп**: файл встраивается только в сборку сервера, образ `web` его даже
  не копирует. Варианты перемешивает сервер, поэтому в файле верный ответ стоит где угодно.
- Факты в вопросах подобраны устойчивые: без рекордов, «текущих» чемпионов и цифр, которые меняются.

Локально без сервера: `npm run db:seed`.

## Движок партии

Игровая логика - чистые функции без сети, базы и настоящих часов: время приходит параметром,
поэтому тесты проигрывают партию целиком с фейковым временем за миллисекунды.

| Где | Что |
|---|---|
| `packages/shared/src/scoring.ts` | Тайминги и очки: `500 + 500 × (осталось / 15 с)`, допуск 300 мс на сеть |
| `packages/shared/src/elo.ts` | Эло: старт 1000, K = 40 первые 10 партий, потом 24 |
| `packages/shared/src/achievements.ts` | Статистика игрока после партии и 12 ачивок с прогрессом |
| `apps/server/src/game/picker.ts` | Подбор 10 вопросов и порядка вариантов |
| `apps/server/src/game/machine.ts` | Машина состояний: лобби, отсчёт, вопросы, раскрытие, отключения, итог |
| `apps/server/src/game/view.ts` | Снимок партии для игрока - без верного ответа до раскрытия |

Фазы: `waiting → lobby → countdown → (question → reveal) × 10 → finished`, отдельно `expired` и `cancelled`.
Каждая операция возвращает новое состояние и события; сервер после каждого шага ставит таймер на
`nextWakeAt()`, а `tick()` закрывает все наступившие дедлайны по порядку - так же партия
восстанавливается после перезапуска сервера.

Принятые решения:

- **Ничья** при равном счёте, без тай-брейка (в ТЗ про неё ничего).
- **3 лёгких + 4 средних + 3 сложных** в любой партии, не только в «Миксе», по возрастанию
  сложности. В «Миксе» не больше 2 вопросов из одной категории. Сначала вопросы, которых не видел
  ни один из игроков, потом самые давние. Порядок вариантов перемешивается один раз на партию.
- **Время ответа** - от старта вопроса до получения ответа сервером. Таймер у игрока 15 с,
  сервер закрывает вопрос через 15,3 с: ответ в допуске на сеть даёт 500 очков, позже - отклоняется.
- **30 секунд на возврат** идут, только пока второй игрок на связи. Ушли оба - отсчёт стоит,
  партия доигрывается по таймерам (без единого ответа - отменяется без рейтинга). Вернулся
  второй - у ушедшего снова 30 с.
- **Лобби** живёт 15 минут с последнего действия (вход, «Готов»), а не с создания.
- **Техническое поражение = обычное поражение** в рейтинге и статистике. Ачивок технические исходы
  не дают (кроме «Эрудита»); ачивки за победы выдаются только на победе.
- **«Знаток темы»** считает победы в 5 категориях; «Микс» - не категория.
- Кроме сценариев из таблицы крайних случаев, тесты гоняют 500 случайных партий со случайными
  действиями трёх игроков и проверяют инварианты на каждом шаге (так нашлась одна ошибка:
  отсчёт до техпоражения не сбрасывался при возврате из отсчёта в лобби).

## Лобби и приглашение

Главная → «Создать дуэль» → шторка категорий → лобби со ссылкой
`https://t.me/q_battle_bot/QuizDuel?startapp=g_<id>` (id - 10 случайных символов `[A-Za-z0-9]`).
«Пригласить» отправляет в выбранный чат карточку бота «Вызов на дуэль» с кнопкой «Принять»
(`savePreparedInlineMessage` + `shareMessage`); если бот не смог её подготовить или клиент Telegram
старый - обычное «Поделиться ссылкой». Ссылку можно и скопировать.

| Где | Что |
|---|---|
| `apps/server/src/game/manager.ts` | Менеджер партий: очередь изменений на партию, таймер, запись в БД, снимки игрокам |
| `apps/server/src/game/repo.ts` | Таблицы `games` и `answers`: полный снимок партии + колонки для запросов |
| `apps/server/src/socket.ts` | События `game:create / join / sync / invite / ready / cancel / leave / answer / forfeit`, каждое через zod-схему |
| `apps/server/src/bot/index.ts` | Карточка приглашения для `shareMessage` |
| `apps/web/src/lib/game.ts` | Клиент: Zustand-хранилище, экран рисуется только из снимка `game:state` |

Как это устроено:

- **Сервер держит активные партии в памяти**, а каждое изменение сразу пишет в `games` полным снимком.
  При старте сервер поднимает незавершённые партии из базы, считает игроков офлайн до подключения
  и сразу закрывает фазы, просроченные за время простоя.
- **Изменения одной партии идут строго по очереди**, поэтому из двух одновременных входов по ссылке
  место получает ровно один, а «Готов» и таймаут не пересекаются. Для одного экземпляра сервера этого
  достаточно; при нескольких экземплярах понадобится блокировка в базе (это пункт «Что дальше»).
- **Вернуться в партию можно без ссылки**: в приветствии сокета сервер сообщает текущую партию игрока.
- **Одна партия на игрока.** Посреди дуэли чужая ссылка и «Создать дуэль» отвечают `busy`
  («Вернуться в партию»). Из открытого лобби - можно: своё пустое лобби отменяется, место
  в чужом освобождается, и бывший соперник видит тост.
- **Таймауты:** лобби без старта живёт 15 минут; соперник офлайн в лобби дольше 60 секунд
  теряет место, и ссылка снова работает. Офлайн создатель лобби не теряет: соперник видит,
  сколько осталось до закрытия лобби.
- **Активно последнее подключение**: при входе с другого устройства прежнее получает
  `session:replaced` и экран «Игра открыта на другом устройстве».

## Партия

Оба «Готов» → 3 с в лобби («Старт через 3…») → 3 с экран VS с крупными 3-2-1 → 10 × (вопрос 15 с →
раскрытие 3 с) → итоги. Отсчёт - одна серверная фаза `countdown` на 6 с, как в утверждённом прототипе;
клиент сам решает, какую часть показать, по дедлайну сервера.

| Где | Что |
|---|---|
| `apps/server/src/game/manager.ts` | `answer()` и `forfeit()` поверх машины состояний, в той же очереди изменений партии |
| `apps/web/src/screens/QuestionScreen.tsx` | Экраны 9-11, 21, 22: вопрос, «ответ выбран», раскрытие, соперник отключился, нет сети |
| `apps/web/src/screens/VsScreen.tsx`, `ResultScreen.tsx` | Экраны 8 и 12 |

- **`game:answer { gameId, questionIndex, optionIndex }`** - номер варианта на экране (порядок
  у обоих одинаковый, перемешивает сервер). Время фиксируется по часам сервера в момент прихода
  события. Ответ на другой вопрос - `wrong_question`, после закрытия - `wrong_phase`, после
  15 с + 300 мс - `late`. Повтор (двойной тап, повторная отправка после переподключения) отвечает
  `accepted: false` и ничего не меняет: засчитан первый ответ. Вторая линия защиты -
  уникальный индекс `(game_id, user_id, question_index)` в `answers`.
- **Верный ответ не уходит на клиент до раскрытия**: пока вопрос открыт, сопернику видно только
  «Соперник ответил», без варианта.
- **Таймер** рисуется по дедлайну из снимка и часам сервера (`time:sync` при каждом подключении
  и возврате из фона даёт смещение часов телефона), поэтому у обоих он одинаковый, а сбитые часы не мешают.
- **Мгновенный отклик**: нажатый вариант подсвечивается сразу, но засчитывает его сервер; если он
  отказал (опоздал), подсветка снимается; если не ответил (обрыв) - выбор уйдёт ещё раз после переподключения.
- **«Выйти из партии?»** - по системной кнопке «Назад» на экране VS и вопроса (на компьютере ещё
  Escape). «Выйти» = `game:forfeit`: сопернику сразу техническая победа, без 30 с ожидания.
- Во время партии свайп вниз не закрывает приложение (`disableVerticalSwipes`), а закрытие
  спрашивает подтверждение. Вибрация: лёгкая на выбор, success / error на раскрытии,
  сильная на победу, тики на последних 3 секундах и на 3-2-1.
- **Итоги**: победа / поражение / ничья, техническая победа и поражение отдельно (кто ушёл -
  сдался или не вернулся за 30 с), счёт, верных из сыгранных, среднее время ответа.
  Рейтинг «Рейтинг 1 016 (+16)», новые ачивки, реванш, «Поделиться результатом» и разбор.

## Надёжность

Сервер - единственный источник правды: клиент после любого переподключения берёт свежий снимок
партии (`game:sync`) и рисует экран только из него.

| Ситуация | Что происходит |
|---|---|
| Свернул приложение, пропала сеть | Партия идёт по таймерам сервера. Сервер замечает «молча» пропавший телефон за ≤ 18 с (пинг 10 с + 8 с), а не за 45 с по умолчанию. После возврата клиент получает снимок с остатком таймера |
| Вернулся из фона, а сокет «мёртвый» | При возврате на экран клиент шлёт короткий `time:sync`; нет ответа за 3 с - переподключается сразу, не дожидаясь пинга |
| Соперник отключился посреди партии | У него бейдж, у второго плашка «Техническая победа через 0:30»; вернулся раньше - отсчёт сброшен, игра с текущего вопроса. Не вернулся - `abandoned`, техническая победа |
| Ответ ушёл в момент обрыва | После переподключения клиент сверяет снимок: сервер ответа не видел, а вопрос идёт - отправляет ещё раз. Ответ идемпотентен, засчитывается первый; время - по приходу на сервер |
| Та же партия на втором устройстве | Активно последнее подключение, прежнее получает `session:replaced` («Игра открыта на другом устройстве» → «Играть здесь»). Соперник при этом не видит ухода |
| Перезапуск сервера (выкатка) | При SIGTERM сервер останавливает таймеры и дописывает начатые изменения, отключения сокетов в этот момент не считаются уходом игроков. При старте партии поднимаются из базы, просроченные фазы закрываются по порядку дедлайнов, клиенты переподключаются сами |
| Сбитые часы телефона | Смещение - по трём замерам `time:sync` (берётся самый быстрый), до замера - грубо по приветствию сокета. Время ответа клиент прислать не может: схема события строгая |
| initData устарел, пока приложение открыто | Сокет отказывает при переподключении - экран «Откройте заново» вместо вечного «Переподключаемся…» |

Тесты: `apps/server/test/reliability.test.ts` - два настоящих клиента `socket.io-client` против
настоящего сервера; время сервера идёт по «перематываемым» часам (`test/jumpClock.ts`), поэтому
30 с ожидания проходят мгновенно. Сценарии: отключение и возврат посреди вопроса, техническая победа
через 30 с, второе устройство посреди партии и «Играть здесь», перезапуск сервера посреди вопроса
(и долгий - 40 с), двойная отправка ответа после реконнекта, ответ из буфера после обрыва, сбитые часы.

## После партии

| Где | Что |
|---|---|
| `apps/server/src/game/settle.ts` | Итоги дуэли: Эло, статистика, по категориям, ачивки - чистая функция |
| `apps/server/src/game/repo.ts` | `settle()` - те же итоги одной транзакцией в Postgres |
| `apps/server/src/game/machine.ts` | Реванш: `offerRematch`, `respondRematch`, `cancelRematch`, `leaveResults`, таймаут 30 с |
| `apps/server/src/stats.ts` | Профиль, история, лидерборд, профиль соперника, разбор (только чтение) |
| `apps/web/src/screens/` | `ResultScreen` (12, 13), `ReviewScreen` (14), `LeaderboardScreen` (15), `ProfileScreen` (16), `OppSheet` (17) |

**Итоги - одна транзакция.** Конец рейтинговой дуэли пишется в базу так: строка партии под
блокировкой `FOR UPDATE` (если `settled_at` уже стоит - возвращается готовый результат, повтор ничего
не меняет); оба игрока под блокировкой, всегда в порядке id (две одновременно закончившиеся партии
одного игрока не теряют изменений и не дедлочатся); Эло по рейтингам, прочитанным под блокировкой;
статистика, `category_stats`, ачивки; финальный снимок партии и `settled_at`. Не вышло (база не ответила) -
снимок пишется без итогов, менеджер повторяет подсчёт (2, 4, 8… с), а после перезапуска сервера
завершённые партии с пустым `settled_at` досчитываются при старте.

- **Эло**: старт 1000, K = 40 первые 10 партий, потом 24 (у каждого свой K), победа 1, ничья 0,5,
  поражение 0. Техническое поражение - обычное поражение. Партия без единого ответа отменяется без рейтинга.
- **Статистика**: игры, победы, поражения, ничьи, серии, точность (верные / сыгранные вопросы),
  среднее время верного ответа, точность по темам вопросов (в «Миксе» у каждого вопроса своя),
  победы по категориям партии. Ачивки считаются в той же транзакции.
- **Реванш**: «Реванш» → у соперника плашка на 30 с «Принять / Отказаться», у предложившего -
  «Ждём ответа» с «Отменить». Согласие создаёт новую партию той же пары в той же категории с новыми
  вопросами и сразу с отсчётом. Оба нажали почти одновременно - второе нажатие засчитывается как
  согласие, партия создаётся одна (операции партии идут по очереди). Отказ, таймаут, уход соперника
  (на главную, в другую игру, закрыл приложение) - кнопка неактивна и подпись, почему.
  После технического исхода реванш недоступен обоим. Состояние реванша лежит в снимке партии и
  переживает перезапуск сервера.
- **Решение: реванш - только сопернику на итогах и в сети.** Предложить реванш можно, пока соперник
  смотрит итоги и на связи. Если он закрыл приложение, пока предложение висит, бот пишет ему
  «Вам предлагают реванш», кнопка открывает итоги, и принять можно в те же 30 секунд. Предлагать
  реванш тому, кто уже закрыл приложение, нельзя: ответить ему было бы негде, а предложение
  повисало бы без ответа. Так пункт 8 ТЗ («оба могут предложить реванш») работает без «висящих» партий.
- **REST**: `GET /api/profile`, `GET /api/leaderboard` (топ-100, только 5+ партий, моё место),
  `GET /api/players/:id` (только того, с кем уже играли - перебрать чужие профили нельзя),
  `GET /api/games/:id/review` (только участникам). `userId` - только из initData.

Тесты: `aftergame.test.ts` (итоги и реванш через менеджер), `settle.test.ts` (подсчёт),
`settle.db.test.ts` (транзакция на настоящем Postgres: повтор, гонка двух партий, откат при сбое,
чтение для экранов; в CI - сервис postgres), `rematch.socket.test.ts` (реванш двумя настоящими клиентами).

Ни одна фича не меняет основную дуэль: все идут через тот же менеджер партий и те же проверки
(документы, «одна партия на игрока», лимиты, zod-схемы).

| Фича | Где | Как устроено | Тесты |
|---|---|---|---|

Технические исходы дают только «Эрудита» | `packages/shared/test/achievements.test.ts`, `settle.test.ts`, `settle.db.test.ts` |

## Настройки, язык, режим без анимаций

Все настройки хранятся на сервере (`POST /api/settings`, приходят в `GET /api/me`), поэтому действуют
на всех устройствах, и применяются сразу, без перезагрузки. Экран 20 «Настройки» - шестерёнка на главной,
назад - системная BackButton.

- **Язык RU / EN**: настройка профиля → `language_code` из Telegram (`ru`, `uk`, `be`, `kk` - русский) →
  английский. Сменили язык - сервер пересылает этому игроку снимок текущей партии, и вопрос приходит уже
  на новом языке (у соперника свой язык, его снимок не меняется; `rev` и таймер те же). Все строки - в
  `ru.json` / `en.json`, тест проверяет, что ключи совпадают и в компонентах нет кириллицы.
- **Режим без анимаций** «Авто / Вкл / Выкл» (`users.reduced_motion`): класс `qd-rm` на `<html>`.
  «Авто» включает его при системном «Уменьшить движение» или на слабом Android (Telegram пишет класс
  устройства `LOW` в User-Agent). Меньше движения, а не ноль: остаются мягкие fade, исчезают сдвиги,
  масштаб, конфетти, блеск и пульсация; таймер обновляется раз в секунду. Тест проверяет, что у каждой
  CSS-анимации есть правило для этого режима. Цвета, вибрация и тайминги игры не меняются.
- **Вибрация** (`users.haptics`): все вызовы идут через один переключатель - выключили, и в партии нет
  ни одной вибрации. **Уведомления от бота** - тумблер для `notifications`; включение без разрешения
  писать сразу спрашивает его у Telegram. **«Как играть»** - шторка с 4 правилами.
- **Онбординг** (`users.onboarded`): новичок видит 3 слайда при первом входе, пришедший по ссылке -
  после партии (документы он уже принял в шторке перед лобби, галочки отмечены).
- **Нет сети**: событие браузера `offline` сразу показывает «Переподключаемся…» и выключает кнопки
  ответа, не дожидаясь пинга сокета; сеть вернулась - сокет проверяется и приходит свежий снимок.
  Ошибки загрузки (главная, рейтинг, профиль, ачивки, разбор, документы) - текст и «Повторить».

Тесты: `apps/server/test/settings.test.ts`, `apps/web/test/settings.test.ts`, `apps/web/test/motion.test.ts`.

## Документы

Перед первой партией игрок ставит две галочки: [Terms of Use](https://telegra.ph/Quiz-Duel---Terms-of-Use-11-06) и
[Privacy Policy](https://telegra.ph/Quiz-Duel---Privacy-Policy-11-06) - страницы в Telegraph на английском, в Telegram они открываются
через Instant View. Новый игрок отмечает их на 3-м слайде онбординга, пришедший по ссылке на игру -
в шторке перед лобби. Без обеих галочек «Начать играть» и «Перейти в лобби» неактивны.

- `POST /api/consents { docs, version }`: `userId` только из initData, нужны оба документа,
  устаревшая версия - `409 stale_version`. Каждое принятие - новая строка журнала `consents`
  (документ, версия, время сервера, IP из `X-Forwarded-For` от своего прокси, User-Agent);
  строки не меняются и не удаляются.
- `game:create` и вход в чужую игру без принятия текущей версии (`DOCS_VERSION`) отклоняются
  с `consent_required`, и клиент показывает шторку. Новая версия документов - галочки снова:
  кто уже проходил онбординг, видит один экран «Мы обновили документы» (`DocsUpdateScreen`) с тем, что изменилось.
- Версия `2026-11-07.2` (7 нояб. 2026): в документах - монеты, покупки за звёзды и возвраты, друзья и приглашения,
  реклама, статистика использования, `/paysupport`. Ссылки на документы - внизу «Настроек» и у бота (`/terms`).

## Безопасность

- **initData проверяется на каждом REST-запросе и при подключении сокета**: HMAC-SHA256
  с ключом из токена бота, сравнение за постоянное время, `auth_date` не старше 24 часов,
  повторяющиеся ключи и дописанные поля отклоняются. `userId` берётся только из проверенных данных.
- initData передаётся в заголовке `Authorization: tma …` и вырезается из логов.
- CORS - только домен мини-аппа. Лимит запросов - на игрока (до входа - на IP).
- Реальный IP игрока: доверяем `X-Forwarded-For` только от Caddy внутри docker-сети.
- Наружу открыт только Caddy; сервер и база доступны лишь внутри docker-сети.
- Каждое событие сокета проверяется строгой zod-схемой: лишние поля и неверные типы - отказ
  `invalid`, сервер не падает. Лимиты: 30 событий за 10 с на подключение, 10 новых игр в минуту.
- Действовать в партии могут только её участники, отменить - только создатель и только до старта.
- Снимок партии не содержит верного ответа до раскрытия.
- Предложить, принять и отменить реванш могут только участники; сам себе ответить нельзя.
- Профиль соперника - только того, с кем уже встречались; разбор - только участникам.
