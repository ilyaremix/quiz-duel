# Разбор трёх обращений из прода

10 ноября 2026, коммиты `e4be414`…`8c42d5f` в main. По каждому обращению: гипотеза и чем она проверена, причина,
исправление и тест (падает до исправления, проходит после), где ещё в коде та же болезнь.

Новые тесты прогнаны дважды: на коммите `43865e8` (main до исправлений) - 8 падают, после исправлений - проходят все.
Проверки целиком: typecheck, ESLint, Prettier, 449 тестов (было 434), сборка - зелёные.

## 1. «Заплатил 100 звёзд за монетки, звёзды списались, а монеты не пришли. Было около 14:05»

По журналу в 14:04-14:05 выкатывалась новая версия.

**Гипотеза.** Платёж прошёл, пока старый процесс уже остановился, а новый ещё не поднялся, и обновление
`successful_payment` до сервера не дошло.

**Чем проверена.** Тест `apps/server/test/payments.db.test.ts`: настоящий grammY-бот и настоящий Postgres,
вместо Telegram - подделка с его правилами (очередь обновлений, подтверждение через offset, `deleteWebhook`
с `drop_pending_updates`). В очереди Telegram лежит оплата, затем «поднимается новый процесс» (`startBot`).

До исправления:

```
× оплата прошла, пока сервер перезапускался: новый процесс её зачисляет
  AssertionError: expected +0 to be 1000
```

**Причина.** `startBot` (`apps/server/src/bot/index.ts`) при первом запуске процесса вызывал опрос с
`drop_pending_updates: true`: всё, что Telegram накопил за время выкатки, стиралось. Звёзды к этому моменту уже
списаны (на `pre_checkout_query` ответил старый процесс), а `grantPurchase` не вызывался. Само зачисление
написано верно: одна транзакция, повтор по `telegram_payment_charge_id` не задваивает. Терялось событие.
На это поведение даже был тест (`botRuntime.test.ts` ждал `[true, false]`) - он закреплял ошибку.

**Исправление** (`e4be414`, `904ecb4`, окно сверки - отдельный коммит после отчёта):

- накопившиеся обновления не выбрасываются никогда;
- сверка с Telegram: `attachPayments` возвращает `reconcile()`, который проходит по `getStarTransactions` и
  зачисляет оплаты, которых нет в таблице `purchases`, и отрабатывает пропущенные возвраты. Запускается при старте,
  каждые 10 минут и через 15 секунд после неудачного зачисления. Источник правды теперь список операций Telegram,
  а не единственное обновление;
- остановка сервера ждёт обработчики, которые уже работают (до 5 секунд), а не обрывает зачисление на середине.

После исправления проходят 5 тестов файла, среди них «база не ответила в момент зачисления: платёж доначисляется
сверкой, ровно один раз» и «остановка сервера ждёт обработчик, который уже зачисляет платёж».

**Почему сверка не раздаёт монеты за всю историю.** Сама она зачисляет только оплаты за последние 7 дней
(`STARS_RECONCILE_DAYS`). Потерянный при выкатке платёж находится за минуты, а оплата месячной давности без записи
в базе - это уже другая история (базу пересоздавали или восстановили из старой копии), и автоматическая раздача
здесь опаснее пользы. Но молчать о ней тоже нельзя: звёзды у игрока списаны. Поэтому такие оплаты бот присылает
владельцу списком (дата, игрок, товар, id платежа); проверив их, он увеличивает `STARS_RECONCILE_DAYS` и
перезапускает сервер - сверка их зачислит. Это покрыто тестом «владелец проверил старую оплату и расширил окно».

**Где ещё та же болезнь** (найдено и закрыто тем же исправлением):

- ошибка в обработчике оплаты (база недоступна): grammY считает обновление обработанным при любом исходе,
  `bot.catch` только писал в журнал - платёж терялся так же. Теперь его добирает сверка;
- возврат звёзд (`refunded_payment`) терялся по тем же двум причинам - сверка отрабатывает и его;
- обработчик, работавший в момент SIGTERM, обрывался выходом из процесса.

**Ограничения, о которых стоит знать.** Пакета монет за 100 звёзд в магазине нет (25, 75 и 150; 100 стоит «Без
рекламы») - механизм потери от товара не зависит. Отметка «до какой операции сверено» хранится в памяти, после
перезапуска история читается заново: это сделано намеренно, пока порядок операций в `getStarTransactions` (по
документации Bot API - от старых к новым) не проверен на живом боте. Сверка проверена на подделке Telegram,
на живом боте не запускалась.

## 2. «Ночью сервер сам перезапустился»

В журнале перед падением - ошибка соединения с базой и Unhandled rejection.

**Гипотеза.** Запрос к базе отклонился в промисе, у которого нет обработчика отказа. Node 22 в таком случае
завершает процесс с кодом 1, Docker (`restart: unless-stopped`) поднимает его заново. Ночью без действий игроков
это может сделать только таймер.

**Чем проверена.**

1. Воспроизведение на настоящем процессе Node: менеджер партий как в проде, двое в очереди быстрой игры с далёкими
   рейтингами (пару сложит таймер, а не запрос игрока), обращение к базе начинает падать.

   До исправления:

   ```
   [error] queue match failed
   Error: Can't reach database server at `db:5432`
       at GameManager.startQuick (apps/server/src/game/manager.ts:923:61)
   Node.js v22.23.4
   exit code: 1
   ```

   После:

   ```
   [error] quick game create failed
   процесс жив, в очереди: true true
   exit code: 0
   ```

2. Тест `apps/server/test/crash.test.ts` - то же через сокеты, со слушателем `unhandledRejection`.
   До исправления (новый модуль `background.ts` заменён пустой заглушкой, иначе файл не импортируется):
   `expected [ Error: Can't reach database server … ] to deeply equal []`.

3. Версия «упал пул соединений pg» проверена и отброшена: `@prisma/adapter-pg` сам подписан на `error` пула и
   соединений.

**Причина.** `scheduleQueue` в `apps/server/src/game/manager.ts`:
`void this.matchQueue().finally(() => this.scheduleQueue())`. Сам проход ошибку ловил и писал в журнал («queue match
failed» в выводе выше), но `.finally()` возвращает новый промис с тем же отказом, а у него обработчика нет. Общего
`process.on('unhandledRejection')` в проекте не было.

**Исправление** (`d965150`):

- таймер очереди ловит отказ; при сбое базы пара не теряется - оба игрока остаются в очереди с прежним временем
  входа, следующий проход пробует снова (раньше при сбое записи партии игроки молча выпадали из очереди);
- `apps/server/src/background.ts`: `background(log, what, job)` - единственный способ запустить дело «вдогонку»,
  сбой уходит в журнал;
- `guardProcess`: пропущенный отказ промиса пишется в журнал и уходит владельцу сообщением от бота, процесс
  работает дальше; необработанное исключение - штатная остановка с кодом 1;
- ESLint для сервера: `@typescript-eslint/no-floating-promises` с `ignoreVoid: false`. Такой код теперь не проходит CI.

**Где ещё та же болезнь.** Правило ESLint на коде до исправлений нашло 14 мест, разобраны все:

- 4 настоящие дыры, запрос к базе без `catch` (исправлены): таймер очереди и три дела в `apps/server/src/index.ts` -
  пуш «заявка в друзья» (`onFriendChanged`), смена настроек (`onSettingsChanged`), вызов друга (`onChallenge`);
- остальные 10 отказаться не могли (ошибка ловится внутри), но переписаны так, чтобы это было видно из кода и
  проверялось правилом: таймеры партий, уведомления бота, цикл опроса Telegram, `syncChatCommands`, вход сокета
  в комнату, сигналы остановки.

## 3. «Купил один билет на тему «Космос», а играю в ней весь вечер»

**Гипотеза.** Есть путь начать партию в платной теме, на котором билет не проверяется и не списывается.

**Чем проверена.** Чтение кода: доступ (`topicOpen`) проверялся только в `create` и `soloStart`, списание
(`spendTopic`) - только в тренировке и на событии отсчёта в лобби. Реванш создаёт новую партию в той же теме и
стартует сразу, мимо обоих мест. Тест `apps/server/test/tickets.socket.test.ts`: два игрока на настоящих сокетах,
один билет, партия в «Космосе», затем «Реванш».

До исправления:

```
× реванш в платной теме - новая партия и новый билет: без билета реванша нет
  expected { ok: true, game: {…} } to match object { ok: false, error: 'locked' }
× тренировка: два запроса сразу - одна партия на один билет
  expected [ { ok: true, … }, { ok: true, … } ] to have a length of 1 but got 2
× билет списать не удалось (база не ответила) - партия в платной теме не начинается бесплатно
  expected { ok: true, game: {…} } to match object { ok: false }
```

**Причина.** `acceptRematch` в `apps/server/src/game/manager.ts` не проверял тему и не тратил билет: один билет и
кнопка «Реванш» давали сколько угодно партий подряд.

**Исправление** (`1e5c71f`):

- реванш в платной теме: доступ создателя проверяется при предложении, билет списывается при согласии; нет билета -
  ошибка `locked`, в приложении сообщение «Эта тема закрыта - откройте её на 1 игру за рекламу или купите»;
- списание стало обязательным шагом с ответом «получилось или нет» (`useTopic` возвращает boolean): партия, которая
  стартует сразу (тренировка, реванш), не создаётся, пока билет не списан;
- если партия после списания не создалась (сбой записи), билет возвращается (`releaseTopic`).

После исправления проходят 6 тестов файла и новый тест на настоящем Postgres в `economy.db.test.ts`
(«два списания сразу проходит одно, несозданная партия возвращает билет»).

**Где ещё та же болезнь** (найдено теми же тестами):

- тренировка: проверка доступа только заглядывала в базу, списание шло потом и без ожидания - два запроса подряд
  давали две партии на один билет (исправлено);
- списание не ждали и результат выбрасывали: при ошибке базы партия шла бесплатно, в журнале оставался `warn`
  (исправлено для тренировки и реванша);
- лобби по ссылке и вызов друга: билет по-прежнему списывается на отсчёте, после перехода состояния. Доступ проверен
  при создании лобби, а открытая партия у игрока одна, поэтому билет на месте; если списание всё же не удалось,
  партия идёт, но теперь это `error` в журнале. Закрыть полностью - резервировать билет при создании лобби и
  возвращать при отмене; это отдельная задача.

**Правило.** Билет в реванше списывается у создателя первой партии, как и в обычной дуэли; соперник в платной теме
играет бесплатно - это правило продукта, оно не менялось. Билет в приложении выдаётся за просмотр рекламы, а не
покупается - на суть обращения это не влияет.
